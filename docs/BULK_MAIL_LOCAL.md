# 業務連絡の一斉メール（ローカル試用）

本番運用は [BULK_MAIL_PRODUCTION.md](BULK_MAIL_PRODUCTION.md) を参照。この文書はPGliteを使ったローカル試用について説明する。

契約済み顧客を選択し、各顧客の業務連絡用代表メールへ送る。代表メールは顧客ごとに1件登録し、請求用メール・担当者メールとは別に管理する。

## 起動と認証

`npm run dev:mail` で起動し、`http://127.0.0.1:3000/bulk-mail` を開く。`.env.development.local` の `LOCAL_AUTH_ENABLED=true` と `LOCAL_AUTH_KEY` でローカル用固定キーを設定できる。開発モード・ループバックホスト・Vercel環境変数なしの条件でのみ有効。接続先の有効管理者が1名の場合にその権限を使い、認証登録やDBセッションは作成しない。セッションは8時間、ログアウト、サーバー再起動で失効する。

固定キー認証を無効にした場合は既存のOTP認証を使用する。通常の `npm run dev` を使う場合は `BULK_MAIL_LOCAL_ENABLED=true` と `BULK_MAIL_LOCAL_DIR=.local-test/bulk-mail` を設定する。

## 操作

1. 「代表メール設定」で各顧客の業務連絡用アドレスを入力し、顧客ごとに保存する。空欄で保存すると登録を解除する。顧客詳細の「業務連絡メール」からも設定画面を開ける。
2. 「作成・確認」で顧客・業種・検索を使って絞り込み、顧客を選ぶ。「表示中を全選択」と個別除外に対応し、フィルター外の選択も保持する。
3. 件名・本文を作成して下書きを保存する。差し込みは `{{会社名}}` のみ。宛名は「ご担当者様」などを本文に記入する。指定の署名は自動で末尾に付く。
4. 「自分宛てにテスト（模擬）」で管理者メールを宛先とするサンプルを確認する。
5. 「宛先・本文を最終確認」で全顧客の宛先、除外理由、会社名を差し込んだ本文を確認する。
6. 確認チェックを入れて「○件に今すぐ模擬送信」を実行する。
7. 「下書き・送信履歴」で顧客ごとの本文と結果を確認する。顧客詳細にも当時の送信先を表示する。

「作成・確認」のテストと一斉送信は模擬処理。実メールは、以下の独立した手動テスト画面から指定の1宛先にだけ送信する。予約配信・添付・HTML編集・到達／開封計測は対象外。

## 実メールを1通だけ手動テストする

`http://127.0.0.1:3000/bulk-mail?view=test`、または「実メールのテスト」タブを開く。顧客・代表メールの登録や選択は不要。テスト用の件名・本文を直接入力するため、顧客の下書き・送信状態は変更しない。

`.env.development.local` に次を設定し、開発サーバーを再起動する。実際のAPIキーはGitへ登録しない。

```dotenv
BULK_MAIL_TEST_ENABLED=true
BULK_MAIL_TEST_TO=受信確認するメールアドレス
BULK_MAIL_TEST_FROM=support@acoru.jp
BULK_MAIL_TEST_API_KEY=開発用のResend送信キー
```

送信元はResendで認証したドメインのメールアドレスを使う。[Resendの送信API](https://resend.com/docs/api-reference/emails/send-email)と[APIキーの管理](https://resend.com/docs/dashboard/api-keys/introduction)を参照。請求用の実送信フラグや本番の環境変数は変更しない。テスト用キーは `RESEND_API_KEY` と分離している。キー未設定でも準備・本文確認は可能で、送信ボタンだけ無効になる。

1. 件名と本文を入力し、「テストメールを準備」を押す。準備はローカル保存だけで送信しない。
2. 送信前の確認で、指定の宛先・送信元・件名・署名付き本文を確認する。件名の先頭に「【テスト】」を付ける。差し込みは使用せず、会社名などは直接入力する。
3. 確認チェックを入れ、「確認した宛先に1通送信」を押したときだけResendへ送信要求を送る。
4. メールサービス受付済みの表示と受付IDを確認し、受信箱・迷惑メールを確認する。「受付」は到達の保証ではない。

APIは管理者・開発モード・ループバックHost・同一Origin・明示的な確認を要求する。宛先・送信元はサーバー設定で固定し、画面やAPI入力から任意の宛先を追加できない。送信処理はワーカーやタイマーに接続せず、準備・ページ表示・再起動で実メールが送られることはない。

準備したメールは `mail_manual_tests` に保存する。同一操作者・同一文面・同一宛先の準備は同じ送信記録を返し、送信開始の記録と[Resendの冪等キー](https://resend.com/docs/dashboard/emails/idempotency-keys)で二重送信を防ぐ。送信後・処理中・結果不明の場合は再送しない。結果不明時はResendの履歴で確認し、再テストが必要なら結果を確かめてから件名か本文を変更する。

## 宛先の扱い

- 代表メールが未登録なら送信対象外。請求用メールや担当者メールへのフォールバック、CC・BCCへの担当者追加は行わない。
- 代表メールの設定画面には全顧客を表示する。送信対象は、有効な会社（`companies.status='active'`）で削除されていない受注済み案件がある顧客に限定する。案件が `status='won'`、または `status='open'` かつステージの `is_won=true` を受注済みと判定する。
- 契約継続・解約日の専用管理はまだない。この判定は「過去に受注済みの有効顧客」であり、契約終了を厳密に扱うには契約状態の追加が必要。
- アドレス単位で送信停止・解除ができる。同じアドレスの顧客には共通で適用する。
- 前後空白を除き、大文字小文字を区別せず重複排除する。同じ代表メールを持つ複数顧客を選択した場合は、先に選択した顧客の1通だけを処理し、残りは重複として表示する。1回最大500社。
- 代表メールの保存には更新番号を使い、別の画面からの上書きを防ぐ。確認後の代表メール・契約状態・送信停止の変更は再確認を要求する。
- 送信開始時に宛先・本文・代表メールの更新番号を確定する。ワーカーも処理直前に再照合し、変更があれば除外する。過去の送信先と本文は代表メール設定の変更で書き換えない。

## 保存と旧データ

CRMの会社・案件は読み取り専用。代表メール、送信停止、下書き、履歴、操作記録は専用PGliteの `.local-test/bulk-mail/db/` に保存する。代表メールは `mail_customer_addresses` に顧客IDで関連付ける。請求テーブルと担当者テーブルは参照・更新しない。CRMのDBへのマイグレーションは不要。

起動時にローカルDBの追加変更を適用する。従来の担当者宛ての下書き・履歴は旧方式として保持し、当時の本文・宛先・完了済み結果を維持する。旧方式の未処理分は停止し、旧下書きの送信や再実行は拒否する。新方式へ自動変換せず、顧客を選択して新規作成する。

ワーカーはNext.js起動中にキューを処理する。画面を閉じても進み、サーバー停止中は停止、再起動で未処理分を再開する。途中で中断した新方式の模擬送信は失敗扱いとなり、失敗分だけ手動再実行できる。結果確認待ちの再実行は拒否する。

同じ保存先を複数のNext.jsプロセスで同時に開かない。独立したテストには `BULK_MAIL_STORE_NAME` で別名を指定できる（英小文字・数字・ハイフン、80文字以内）。ローカルデータはGit・デプロイ・ビルド追跡対象から除外する。

`VERCEL` または `VERCEL_ENV` が設定された環境では、一斉メールの画面・API・ワーカーを無効にする。本番反映と顧客への実送信は別作業。
