# 自由記述から業務データへ

2026-09-30。実装仕様 v2.0 に対応する追加機能。Next.js App Router、既存のNeon/Postgres直接SQL、Zod、DeepSeek、既存の認証・案件提案を使用する。新しいORM・AI SDK・クラウドストレージは追加しない。

## 境界と保存先

```text
貼り付け / MD・TXT / PC側同期CLI
  → raw_documents（論理文書）
  → raw_document_revisions（固定版・全文・SHA-256）
  → extraction_runs → extraction_chunks → extraction_items
  → 人間の編集・承認
  → 明示的な適用
  → activities / tasks / deal_decisions / work_logs
  → CRM検索・工数集計
```

原文の正本はDB内のrevision。本文・基準日・hash等はDBトリガーで上書き/削除を禁止する。外部AIへの送信許可だけは監査付きで変更できる。原文はMarkdownとして実行せず、テキストとして表示する。

リポジトリやPCのMarkdownは入力元。サーバーのローカルディスクへ原本を保存しない。Vercel実行環境からPCのフォルダを読まない。添付バイナリ、PDF/OCR、音声変換、メールの自動収集は対象外。元からあるfilesテーブルはURL/メタデータ管理のまま。

RAWと抽出候補は登録者本人だけが参照する。管理者も他人のRAWを読む特別権限を持たない。承認してCRMへ反映した業務事実は既存CRMと同じ社内共有。原本へのリンクは所有者に限り開ける。

## 有効化

全フラグは文字列trueでのみ有効になる。既定はfalse。

| 環境変数 | 制御 |
| --- | --- |
| RAW_INGEST_ENABLED | Web原本登録。同期登録にも必要 |
| RAW_EXTRACTION_ENABLED | 抽出開始・再試行。保存・閲覧は独立 |
| RAW_APPLY_ENABLED | RAW候補のCRM適用。レビューとは独立 |
| RAW_SYNC_ENABLED | 同期API、トークン発行・失効画面/API |

認証は既存のMFA/session。DB接続とDeepSeekの設定は既存環境変数を使用する。DeepSeekのキーをCLIへ渡さない。フラグを停止しても既存CRMを停止しない。保存済みRAWの読み取りAPIとレビューは認証下で残る。同期トークンはフラグ停止で利用不可となり、再有効化前に失効する場合は管理APIの失効を使う。

アプリ公開前に007〜011を順に適用する必要がある。既存レポートも011の共通ビューを使用する。コードだけを先に本番へ出さない。

## Paste / Upload

1. ログイン後、/assistant「AIアシスタント」を開く。
2. チャット入力の「業務メモを保存」で自由文を保存するか、「ファイルを追加」でUTF-8の.md/.txtを保存する。「資料・原本」内でも貼り付け・選択・ドロップで追加できる。
3. 原文の基準日と外部AI許可は任意。必須は本文/ファイルだけ。AIを使わず保存できる。
4. 文書を選ぶと版の一覧と全文が表示される。
5. 許可した版で「抽出を開始／再開」。候補の引用・行番号・日付・関連先を確認する。
6. 関連案件を検索・選択し、必要な内容を編集して承認する。工数は案件なしの未配賦でもよい。
7. 「承認済みの内容をCRMへ反映」で初めて業務レコードが作られる。
8. 活動/タスク編集、案件詳細の出典一覧、工数明細から原本へ戻れる。

「この原本について相談」で同じアシスタントの会話へ戻り、許可した固定版を読んだ回答を得られる。通常の相談文は原本へ自動登録しない。独立した「業務ログ受信箱」「実績工数」の画面・メニューは廃止し、資料・原本は `/assistant?view=materials`、工数分析は `/assistant?view=work` に統合した。会話中は `/assistant/<thread-id>` のままパネルを切り替える。旧 `/raw` と `/work-logs` は出典互換の転送だけを残し、既存の原本・候補・工数・同期APIは保持する。

1ファイル256 KiB、一度20件まで。Web/CLIは選択した文書を2 MiB以下のJSONリクエストへ自動分割し、大きな一括送信を避ける。拡張子、UTF-8、バイナリ/制御文字、サーバー計算hash、IDを検証する。JSONの不正UTF-8も拒否。バッチでは不正ファイルだけが失敗する。

貼り付けは入力セッションごとの安定キー。同名アップロードは同じ登録者の同じ論理文書として扱う。別文書なら別のファイル名にするか貼り付けを使う。ローカル同期ではファイル名ではなく専用UUIDが同一性を保持する。

「本文を編集して新しい版を作る」は元の本文を残す。同一文書・同一本文の再送は既存revisionを返す。内容が同じなら基準日等のmetadataだけを変えて新revisionを作ることはできない。必要な業務日付はレビューで訂正する。

## 抽出と再解析

会話用agent_runsはthread必須・1実行1提案で、RAWの分割処理と状態が異なるため専用の抽出テーブルを追加した。会話本文の自動バックフィルはしない。

- 実行にはextraction/schema/promptの版と実際のmodelを保存。同条件の既存実行を再利用する。「新しい実行として再解析」だけが別実行を作る。
- 5000文字を目安に改行で分割。長い単一行もサロゲートペアを切らず分割し、全ての範囲をDBに記録する。
- 1HTTPリクエストは1部分。ブラウザーが次の部分を順次呼び、画面を閉じた後は再開操作で残りを処理する。常駐ワーカー/cronは追加していない。
- 部分失敗を成功と表示しない。完了済み部分は維持。2分を越えた実行中部分は再試行時に失敗扱いにし、attempt IDで遅い旧応答を排除する。
- 外部AIへ送る直前に版の許可を確認。停止・不許可でも保存済み原本は維持する。
- AIにはemit_candidatesという候補返却だけを渡す。自由SQL、URL取得、CRM操作ツールは渡さない。原文内の命令はデータとして扱う。
- quoteが原文のsubstringかを検証し、行番号はサーバーで再計算する。不正な候補は部分全体を失敗にして再試行を促す。
- IDはAIに生成させない。会社名と案件名の完全一致が一意な場合だけ自動解決。未登録・類似名・同名複数はレビューへ。顧客や案件を勝手に作らない。
- 業務日と期限は原文の日付表現から取得。「今日/昨日/明日」は原文の基準日がある場合だけ解決する。来月等の曖昧表現はnull。受領日を業務日に流用しない。
- 担当者、満足度、確度、契約金額、売上、入金を推測して埋めない。タスク担当者は未指定。通常の優先度mediumは既存CRMの初期値。
- 各候補は独立した承認状態。案件ごと・候補ごとの1操作として既存agent_change_requests/apply_agent_changesへ接続するため、1提案10操作の制限を越えない。
- 意思決定は履歴だけを追加し、現在の案件方針を置き換えない。意思決定日と登録日時を分ける。
- 工数だけは案件未配賦を許すため、同じapply_raw_itemトランザクション内の工数分岐を使う。

## 同一性・競合・監査

安定キーには文書ID、種別、正規化した引用・概要、日付/関連先/工数の構造的な意味を使用し、行番号やモデル発行UUIDを使わない。

sameは以前の候補へ案内し、新規作成しない。newも未承認候補として保存するだけ。changed/ambiguousは以前の候補と現在のCRMを表示し、「別の事実として新規作成」を人間が明示確認するまで承認できない。表現変更を完全な意味同一性として判定することは保証しない。

原文から記述が消えてもCRMを削除しない。原文再解析による既存レコードの自動上書きは行わない。更新したい場合は既存CRM編集画面で行う。

適用は1トランザクションでactor・原本所有者・候補状態・引用・関連先・案件権限・案件版を検証する。文書/候補ロックとstable key、一意制約で二重作成を防ぐ。承認後の案件変更はconflictとなり、最新状態を見て再承認が必要。複数候補を先に承認して同一案件へ順に反映すると、先の反映で版が進むため後の候補は再承認が必要になる。

適用済みの業務ID → 提案/監査 → extraction item → run → RAW revision → documentの経路を保持する。work_logsはextraction_item_idに一意FKを持ち、監査にも出典を記録する。後から手動編集した業務レコードと原文の違いは保持される。

## ローカル同期

必要なものはNode.js、既存pnpm依存関係と同期専用トークン。DB credentialやAI keyは不要。

1. AIアシスタントの「資料・原本」内の「ローカルフォルダ同期の認証」でトークンを発行。表示は一度だけ。DBにはSHA-256のみ保存される。
2. PCの秘密情報管理機構等でRAW_SYNC_TOKEN環境変数を設定。コマンド引数、履歴、リポジトリへsecretを書かない。
3. 次のコマンドで対象と同一性を確認する。rootは明示したフォルダだけ。

```powershell
pnpm raw:sync --root "C:\BusinessNotes" --dry-run
pnpm raw:sync --root "C:\BusinessNotes" --url "https://your-crm.example"
```

RAW_SYNC_URL環境変数でも送信先originを指定できる。HTTPS必須（localhost/127.0.0.1のみHTTP可）。認証ヘッダー付きリダイレクトは追わない。全てのsymlink/junction、隠しファイル/ディレクトリ、.env*、.git、node_modules、バイナリ、対象外拡張子を除外する。

stateはroot直下の.acoru-raw-sync.json。同期対象外かつこのリポジトリではgitignore対象。文書UUID、相対パス、端末内file ID、最後にackを受けたhash/document/revisionを保存する。本文・tokenはstateに保存しない。

初回送信前に文書の同一性だけを保存する。サーバーから検証済みackを受けた後にのみackを更新。失敗後は同じ文書UUIDで再送する。未変更ファイルは送らない。移動だけなら同一本文を再送してサーバーmetadataを更新し、revisionは増えない。

既知file ID、または移動元が一意に特定できる同一hashでrename/moveを追跡する。不明ならidentity_reviewで止めて該当ファイルを送らない。同じrootに未解決の削除ファイルがある場合も、未知ファイルを勝手に新規扱いしない。

明示的に同一性を判断できた場合:

```powershell
pnpm raw:sync --root "C:\BusinessNotes" --dry-run --move "old.md=new/place.md"
pnpm raw:sync --root "C:\BusinessNotes" --url "https://your-crm.example" --move "old.md=new/place.md"
pnpm raw:sync --root "C:\BusinessNotes" --url "https://your-crm.example" --new "separate.md"
```

--moveは移動元が端末から消え、移動先が存在する場合だけ有効。--newは別文書であることを人間が決める指定。ローカル削除はlocal_missing_server_preservedと表示し、サーバー原本を削除しない。stateを削除すると同一性が失われるため、ノートと一緒に安全にバックアップする。異常終了後に.lockが残った場合は、同期プロセスが無いことを確認してロックだけを手動解除する。

トークンは登録者本人のRAW ingestだけに使用可能。読取・AI起動・承認・CRM適用は許可しない。30日失効、画面で個別失効・再発行可能。同期で保存した版のAI許可は必ずfalse。後からWebで本人が許可する。

## 工数・分析

1.5h / 1.5時間 / 1時間30分 / 90分を90分へ、30mを30分へ正規化する。正の整数、上限1440分/記録。時刻範囲や予定から実績を推定しない。引用を含む行に予定・見込み等があるものも拒否する。作業者は推測しない。レビューで既存の利用者を選択できる。

AIアシスタントの「工数分析」はconfirmedだけを日別・顧客別・案件別と案件未配賦で集計。削除済み顧客/案件とcancelledは除外。日付範囲を指定可能。明細表示は最新100件、集計値は条件一致全件。「この集計について相談」で条件を会話へ渡せる。キャンセルの一般UI・直接工数入力は今回の対象外。

既存AI検索ビューには確認済み工数だけを追加。get_work_metricsは同じ集計関数を使う。私有RAW本文は共有CRM検索には追加せず、アシスタント専用のlist_business_materials / read_business_materialから本人の許可済み固定版を参照する。読取は4,000文字ずつで、未取得部分を全文と扱わない。原本を読んだ実行では通常の更新案を作らず、出典付き抽出候補の承認・反映へ案内する。同期トークンはAIへ渡さない。既存レポート/ダッシュボードとAI検索は生存中の同じ顧客・案件・関連記録を対象にし、期限判定をJSTで揃える。

案件金額・確度加重金額は既存の予測指標。請求送付額、入金、売上計上、LTV、利益は同一視しない。原価・収益認識モデルが足りないため、今回の工数集計から利益・LTVを表示しない。

## 未確認・限界

- 独立Neonプレビューへのmigrationと、Vercel/実DeepSeekでの合成データフローを検証済み（[実装結果](RAW_IMPLEMENTATION.md)）。実業務データの抽出精度、AI契約/保持条件、負荷限界は別途確認。
- 外部AIの契約・データ保持・学習利用条件はコードから確認できない。許可前に組織として確認が必要。許可取消は既に送信した情報を取り戻さない。
- 1ファイル256 KiB、1部分最大50候補、AI応答上限4096 tokens。候補過多・出力途中打切りは失敗とし黙って部分反映しない。必要なら入力文書を分ける。
- 意味的重複は完全には解決できない。曖昧候補の人間による誤承認を含め、引用と既存CRMの比較が必要。
- 同時実行のテストはPromise並列をPGliteで検証する。実Postgresの複数接続負荷/ロック競合は別環境で確認する。
- 社内単一組織モデル。マルチテナント分離は追加していない。既存OTPログインは設定された1利用者に固定される。
- DBバックアップ/保存期間/原本削除要件は運用設計で扱う。immutable revisionを通常APIから消す機能は追加しない。
