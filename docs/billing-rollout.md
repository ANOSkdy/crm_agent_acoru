# 請求管理の運用

既存CRMの `/billing` に管理者向け請求管理を提供する。請求設定・請求書・送信履歴は `billing` スキーマに保存する。

## 請求先と請求書

- 請求先はCRM会社に紐付ける。既存8社の宛先は、取り込み元Excel「顧客マスタ」の顧客IDと会社名の一致を確認して登録する。
- 保存済みの設定で請求担当者が未選択なら、登録された請求用メールアドレスを使用する。担当者を明示的に選択した場合のみ、その担当者のメールを今後の請求に反映する。
- 請求先の有効化と、自動処理・メール送信の設定は独立している。無効な請求先は月次作成・送信の対象にしない。
- 内容確認済みで有効化した顧客は、初回から送信待ちになる。未確認で仮作成された当月分は、個別に編集していない場合に限り、設定の確認完了時に送信待ちへ進む。明示的な保留は解除しない。
- 作成済み請求書は宛先・金額・件名・支払期日のスナップショットを保持する。請求先設定の変更で過去の請求書を上書きしない。

## 自動処理とメール送信

Vercel Cronは毎月1〜3日・25〜28日の日本時間9時に実行する。自動処理が有効な場合、25〜28日は当月の未作成分を補完する。メール送信も有効な場合のみ、1〜3日に前月分の未送信請求を処理する。古い未対応分は一括送信しない。

実宛先の登録は `BILLING_ALLOW_REAL_RECIPIENTS=true` で有効にする。メール送信にはproduction環境、`BILLING_LIVE_SEND_ENABLED=true`、実宛先の登録設定、送信サービスのキーが必要。送信が停止している間は送信操作を無効にし、送信履歴や送信用PDFを生成しない。

`node scripts/billing/check-config.mjs acoru.jp` は設定の有無と送信元ドメインを読み取りだけで確認する。認証情報や宛先は出力せず、メールを送信しない。保護された環境変数はローカルへの取得時に値が非表示になるため、本番のビルド環境で確認する。送信専用のAPIキーでドメイン参照が拒否された場合は、ドメイン認証を別途確認する。

初期化後は全請求先を無効、自動処理を停止とする。請求元情報と契約内容を保持し、宛先・金額を確認した顧客から有効にする。再開前に旧GASの作成・送信トリガーが停止していることを確認し、二重稼働を避ける。

## 送信障害

送信開始前にPDF・宛先・本文・一意な送信IDを保存する。同じ請求の本番送信レコードは1件に制限する。通信タイムアウトや受付後のDB更新失敗では処理中・確認待ちとして、自動再送を停止する。メールサービスの受付結果と照合して復旧する。

## データ初期化

通常の無効化は履歴を保持する。ユーザーが全請求書の削除を明示した初期化では、自動処理と請求先を停止し、送信中の処理がないことを確認する。取り消し用のローカル退避を作成し、宛先の対応関係を照合した上で、請求書・保存PDFを含む送信履歴・旧実行履歴を同一トランザクションで削除する。原本Excel、請求元設定、実顧客の契約内容は保持する。原本・宛先・退避データをGitやデプロイ対象に含めない。

## 開発時の確認

`pnpm test:billing` は独立したPGliteと模擬メールサービスを使用する。本番DBへのテストデータ投入や実メール送信は行わない。型チェック・lint・ビルドと合わせて、請求無効時の停止、宛先保持、重複送信防止を確認する。
